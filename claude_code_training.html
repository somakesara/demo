01
What Claude Code is

Claude Code is an AI-powered terminal that reads your codebase, reasons about it, and executes engineering work — with your approval.

It is not autocomplete. It is not a search engine over Stack Overflow. It is a system that holds your entire codebase in working memory, understands intent expressed in natural language, and executes changes through a deterministic tool layer — bash, file I/O, git, test runners — while you retain final judgment on every action.

Collapse ↑ / Expand ↓
Why this matters for junior engineers
Riya joined a fintech team six months ago. The payment microservice had 28,000 lines of Java she'd never touched. Her senior engineer was on leave. A regression surfaced at 11 PM: transaction confirmations were timing out for users in Southeast Asia. Before Claude Code, she'd have spent three hours tracing call graphs, reading logs, and guessing. Instead, she described the symptom. Claude read the service, found the blocking JDBC call behind a CDN with 300ms added latency for that region, proposed a fix, and ran the integration tests. She shipped a patch at midnight. The senior engineer reviewed it in the morning and called it clean. That is what Claude Code actually does in practice.
What it is

A codebase-aware collaborator

Claude Code reads your entire project — source files, configs, test suites, git history — and maintains that context across a session. When you ask it to fix a bug, it finds the root cause, not just the symptom. When you ask it to refactor, it traces the dependency graph. It knows your code better than any fresh pair of eyes in the first hour.

What it is not

A replacement for engineering judgment

Claude Code proposes. You decide. It generates a diff; you review it. It runs tests; you interpret the results. It drafts a commit message; you approve it. The system is designed to amplify your judgment, not circumvent it. Every destructive action — git push, file deletion, production command — requires explicit approval.

The key mental model
Think of Claude Code the way you think of a senior engineer who just joined your team. They are fast, technically strong, and tireless. They will implement exactly what you ask. The partnership works when the division of responsibility is clear. It breaks when you treat Claude as an oracle rather than a collaborator.

Architecture

Three layers: intent processing, deterministic tool execution, and an adaptive feedback loop.

Understanding how Claude Code actually works — not the marketing version — tells you where it is reliable, where it can fail, and how to structure your requests to get the best results. The architecture is not magic. It is a language model orchestrating a set of deterministic tools, with a feedback loop that lets it iterate on failures.

Collapse ↑ / Expand ↓
Layer 1: Intent Processing

Natural language → structured reasoning

Semantic

What happens

Claude receives your prompt along with the current context window: open files, recent terminal output, git status, any CLAUDE.md documentation you've written. It uses this to build a semantic model of your intent — not keywords, but the goal behind the words.

Why this matters

"Fix the payment bug" and "resolve the NullPointerException in PaymentService line 84" produce very different planning. The richer your context, the more accurate the intent model. Investing 30 minutes in a good CLAUDE.md pays dividends on every session.

What can go wrong here

Ambiguous prompts produce ambiguous plans. If Claude cannot distinguish between "clean up the build artifacts" and "remove all compiled output including shared libraries used by other services," it may choose the wrong interpretation. Specificity is a form of safety.

Layer 2: Tool Execution

Deterministic operations on real systems

Deterministic

The tool surface

Claude Code's tools are deterministic: Read, Write, Edit, Glob, Grep, Bash, Git (via Bash), WebFetch, Agent. Each tool has a defined input/output contract. When Claude calls Grep, it receives real filesystem results. When it runs Bash, it gets real stdout/stderr. The model's reasoning is probabilistic; the tools are not.

Parallelism

Claude calls independent tools in parallel. When analyzing a service, it might simultaneously grep for all call sites, read the service class, and check test coverage — then synthesize the results. This is why codebase analysis feels fast: it is parallel I/O, not sequential reading.

Permission layer

Risky tools — anything that modifies files, runs shell commands, or touches remote systems — require your approval unless you've pre-authorized them in .claude/settings.json. You can grant always-allow for specific tools in trusted contexts and require confirmation for everything else. This is your safety layer.

Layer 3: Feedback Loop

Observe → reason → iterate

Adaptive

What happens

After each tool call, Claude observes the result and updates its reasoning. A test that fails is not a stop condition — it is new information. Claude reads the stack trace, locates the assertion that failed, understands why the refactor broke it, and adjusts. This loop continues until tests pass or Claude hits a genuine blocker.

The iteration budget

Claude will iterate on failures, but it has a practical limit. After several failed attempts at the same problem, it will surface the blocker to you rather than continue spinning. This is intentional — it prevents runaway loops that burn tokens without making progress. When Claude says "I'm stuck," take it seriously.

Context preservation across iterations

The full conversation — every prompt, tool result, and intermediate reasoning step — stays in the context window until it is summarized. This means Claude remembers what it tried, why it failed, and what constraints you gave it. Long sessions eventually compress earlier context; be explicit about critical constraints if a session runs long.

They cost more tokens but enable work at a scale a single session cannot hold.

Capabilities

Core capabilities are available on day one. Advanced patterns take two to four weeks to develop fluency with.

The mistake most junior engineers make is using Claude Code only for autocomplete-scale tasks: "write this function," "explain this line." Those use cases barely touch the capability surface. The real leverage comes from session-scale and codebase-scale tasks — the ones that would normally take days.

Collapse ↑ / Expand ↓

Core: Codebase navigation and explanation

Ask Claude to map a service, trace a data flow, or explain a complex function. It reads the relevant files, traces dependencies, and produces a structured explanation in plain language. Especially powerful for onboarding: "explain the auth flow from login request to session token" saves hours of reading.

Core: Targeted edits with diff preview

Describe the change you want. Claude proposes a diff. You review and approve. The edit tool sends only the changed lines — not a full file rewrite. For small changes in large files, this is both safer and faster than manual editing. Claude won't touch anything outside the scope you described.

Core: Test execution and failure diagnosis

Tell Claude to run your test suite. It executes, streams output, reads failures, identifies root causes, and iterates on fixes. If a test was flawed (wrong assertion, missing mock), Claude will tell you — it doesn't blindly patch tests to pass. The distinction between a failing test revealing a bug and a failing test revealing a bad test matters, and Claude understands it.

Core: Git workflow — branches, commits, PRs

Claude authors semantically meaningful commit messages, stages the right files, pushes to the correct branch, and creates pull requests via GitHub CLI. It will not force-push to main, will not commit files that look like secrets, and will not skip pre-commit hooks. These are hard guards, not best-effort reminders.

Advanced: Multi-phase refactors with rollback planning

For large refactors — async migration, dependency upgrade, API redesign — Claude plans in phases, executes each phase, runs tests, and checkpoints progress. If a phase fails, it can roll back to the last clean state. You approve the plan before execution begins and each phase before it runs.

Advanced: Parallel multi-agent tasks

Security audits, comprehensive code reviews, large codebase migrations — these require more context than a single session can hold. Spawn specialized agents in parallel: one agent reviews security, another checks performance, a third audits compliance. Results are synthesized into a single report. This is how senior architects work at scale.

Advanced: Hooks and automated workflows

Claude Code hooks allow you to attach behavior to events: before a tool runs, after Claude stops, when a file changes. Teams use hooks to enforce standards automatically — run the linter before every edit, post a summary to Slack when Claude finishes a session, require security review before any bash execution. Hooks are shell commands, not Claude invocations; they are deterministic and fast.

Advanced: Remote agents and scheduled tasks

Schedule Claude agents to run on cron — nightly security scans, weekly dependency audits, automated test generation for new code. Remote agents run in Anthropic's infrastructure, not your machine, and post results wherever you configure (Slack, GitHub Issues, email). As of May 2026, this is available in Claude Code's Pro and Enterprise tiers.

The leverage gradient: A function-level task saves minutes. A session-level task (debug, refactor a class) saves hours. A codebase-level task (migration, audit, architectural analysis) saves days to weeks. Your time investment in learning Claude Code's advanced patterns pays compounding returns on every large task you face.

Three economics mistakes junior engineers make

Mistake 1: Using agents for everything
Costly

What happens

Spawning a multi-agent loop for a task that a single focused prompt could handle. Agents are 3–10× more expensive than single-session interactions. They are the right tool for tasks that require more context than one session can hold — not for every question.

The fix

Start with a single, well-scoped session. Narrow the scope. If the task genuinely requires 5+ independent research threads that cannot be sequenced, then use agents. Otherwise, a focused session is faster, cheaper, and easier to audit.

Mistake 2: Broad prompts that force exploration
Wasteful

What happens

"Refactor the payment system" forces Claude to explore the entire codebase before it can plan. You pay tokens for exploration that you could eliminate by scoping: "Refactor PaymentService.processOrder() to use CompletableFuture. Keep the HTTP contract unchanged."

The fix

Know your codebase well enough to point Claude at the right files. Use Claude to explore unfamiliar code, then use that knowledge to scope future tasks tightly. Exploration is a one-time cost; tight prompts pay it back on every subsequent task.

Mistake 3: Ignoring prompt cache for repeated tasks
Missed savings

What happens

Running the same analysis repeatedly — daily security reviews, nightly test runs — without using prompt caching. The first call costs full price. Subsequent calls within 5 minutes cost 10% of input tokens. For scheduled agents, cache hits can reduce costs by 80–90%.

The fix

For scheduled or repeated tasks, structure your system prompt to be cache-friendly: stable content first, variable content last. The Anthropic SDK supports prompt caching directly. Teams running nightly audits cut costs from $20/run to $3/run with this pattern alone.

Track your costs: Anthropic's console shows token usage per API key. Set a monthly budget. Review it weekly until you understand your team's usage pattern. Most teams find their costs stabilize after 4–6 weeks as engineers develop better prompting habits. Runaway costs almost always trace to one of the three mistakes above.

Security architecture and risks

Claude Code operates across three trust boundaries. Understanding them is not optional if you work with sensitive code.

Claude Code reads your files, executes shell commands, and sends context to Anthropic's API. In a regulated environment — fintech, healthcare, defense — this is not a minor detail. The system has strong defaults, but you need to understand where the trust boundaries are and what they mean for your specific risk profile.

Collapse ↑ / Expand ↓
Boundary 1

Your local machine

Claude Code reads files and executes commands with your user permissions. If your machine is compromised, Claude Code is compromised. Standard hygiene applies: locked screen, strong credentials, full-disk encryption, no running Claude Code as root.

Boundary 2

Anthropic's API

Your prompts and codebase context travel to Anthropic's servers for inference. Anthropic is SOC 2 Type II certified and contractually commits not to train on customer API data. This is still the cloud — not zero-trust. Treat it as a trusted third party, not your own datacenter.

Boundary 3

Third-party integrations

MCP servers extend Claude's reach to GitHub, Google Drive, cloud CLIs, internal APIs. Each integration is a trust extension. Every server you add expands the blast radius of a compromise. Audit each one. Grant minimum necessary scope.

Threat model

Prompt injection via untrusted content
Real risk

How it works

An attacker embeds instructions in a code comment, error message, or file that Claude reads. If Claude treats the embedded content as instructions rather than data, it may take unintended actions — exfiltrating code, modifying files, or changing behavior to mask a backdoor.

Claude's protection

Claude Code's training includes prompt injection resistance. It is more robust than a naive LLM, but not theoretically immune. Adversarial content crafted specifically to exploit this attack surface remains a realistic concern in high-value targets.

Your mitigation

Do not ask Claude to act on untrusted content without inspection. Never pipe raw API responses, user-supplied data, or external log files directly into a Claude session without reviewing them first. Treat this like SQL injection: the defense is architectural, not just relying on the framework.

Credential and secret exposure
Real risk

How it works

Claude reads a .env file, a hardcoded credential in a config file, or an AWS key in git history. That content travels to Anthropic's API. Even with contractual data protections, this is an unnecessary exposure vector.

Your mitigation

Never store secrets in files Claude can read. Use proper secrets management: AWS Secrets Manager, HashiCorp Vault, environment variables injected at runtime (not stored in files). Add .env and credential patterns to your .gitignore and verify Claude Code respects it. If you accidentally expose a secret, rotate it immediately — assume it is compromised.

Claude generates vulnerable code
Persistent risk

How it works

Claude generates code that passes your tests but contains a SQL injection, path traversal, SSRF, or race condition. Your tests don't exercise that path. The code ships. The vulnerability is discovered in production.

Why this persists

Claude is not a security scanner. It produces code that is plausible and functional but does not perform formal security verification. Security properties that require reasoning about adversarial inputs — trust boundaries, injection vectors, authorization checks — are exactly the places where language model generation is weakest.

Your mitigation

Review all AI-generated code on security-critical paths. Run SAST (SonarQube, Semgrep) on every PR. Fuzz test input handling code. Treat Claude as a junior contributor who is technically strong but has never operated under adversarial conditions.

Destructive command misinterpretation
Manageable

How it works

An ambiguous prompt produces a destructive interpretation. "Clean up old data" becomes a command that drops a production table. "Remove the test environment" removes more than intended.

Claude's protection

Claude Code requires explicit approval for destructive operations. It will show you the command before running it, flag irreversible operations, and refuse to force-push to main or skip pre-commit hooks without your explicit request.

Your mitigation

Be specific. "Remove all *.o files from the build/ directory" is unambiguous. "Clean up old data" is not. The specificity of your prompt is your first line of defense against misinterpretation. Never approve a bash command you have not read.

Regulated environments: PCI DSS, HIPAA, FedRAMP, and similar frameworks impose constraints on where customer data can travel. Before using Claude Code in a regulated environment, work with your security and compliance team to understand whether codebase context (which may include PII-adjacent data structures, schema definitions, or configuration) is permissible to send to Anthropic's API. For highly sensitive systems, consider whether air-gapped or on-premise alternatives exist.

This walkthrough follows a real class of problem: a legacy Java service with synchronous I/O that degrades under load. The goal is an async migration using CompletableFuture. The walkthrough shows exactly what you type, what Claude does, and what decisions remain yours — not as a summary, but as a trace of the actual session flow.

The situation
You are three months into the job. The payment-service has been escalated by the SRE team: p99 latency is 840ms under 200 requests per second. The SLA is 500ms. The service was written four years ago by engineers who are no longer at the company. It has 31,000 lines of Java, one architecture diagram that is out of date, and test coverage at 61%. Your senior engineer is at a conference. You have a week to ship a fix.

Limitations and failure modes

Claude Code fails in predictable ways. Knowing the patterns is what separates engineers who ship safely from engineers who get surprised.

Every capability has a failure mode. Some failures are correctable mid-session. Others require you to step back and change your approach entirely. The engineers who get into trouble with Claude Code are not the ones who expect too little — they are the ones who expect too much, in the wrong direction.

Collapse ↑ / Expand ↓
Failure mode 1: Context window exhaustion
High impact

What happens

Claude's context window is 200,000 tokens (~150,000 lines of code). Large monolithic codebases exceed this. When Claude cannot fit all relevant files into context simultaneously, it sees only part of the picture. It may miss a dependency in a distant module, an override in a parent class, or a constraint defined in a file it hasn't read.

How to recognize it

Claude produces a change that is locally correct but breaks something elsewhere. Claude asks clarifying questions about things that are defined clearly in another file. Claude's plan ignores a component you know is relevant.

Mitigation

Narrow scope before starting. Point Claude at specific files rather than asking it to explore broadly. Use the Explore subagent to identify relevant files first, then scope the main session tightly. For very large codebases, break tasks into sequenced sessions with explicit handoff context.

Failure mode 2: Implicit constraint blindness
Common

What happens

Your codebase has unwritten rules: all database calls must complete within 200ms, all new endpoints require X-Ray tracing, all monetary amounts must be handled with BigDecimal, never double. Claude does not know these rules unless you tell it. It will generate code that violates them.

How to recognize it

Code review catches things Claude missed. Your CI linter fails on patterns Claude used. A senior engineer asks "why isn't this using BigDecimal?" You feel like you're constantly correcting the same class of mistakes.

Mitigation

Write a CLAUDE.md in your project root. Document conventions, non-obvious constraints, team decisions, and anti-patterns. Claude reads this file at the start of every session. 30 minutes invested in a good CLAUDE.md eliminates a category of recurring corrections permanently.

Failure mode 3: Confident hallucination of API details
Subtle

What happens

Claude references a library method that does not exist in your version, uses a configuration key that was deprecated in a release after its training cutoff, or describes a framework behavior that applies to a different major version. The code compiles but fails at runtime in a non-obvious way.

Why this is hard to catch

Claude is confident and fluent. It does not hedge on things it is wrong about. A hallucinated API call looks identical to a correct one in the generated code. You need a running system — not a language model — to validate API surfaces.

Mitigation

Tests are your ground truth. If code compiles but tests fail on a specific method call, check the actual API documentation — do not accept Claude's explanation of the failure as authoritative. Use your IDE's autocomplete to validate API surfaces before approving a diff.

Failure mode 4: Scope creep in "cleanup" tasks
Annoying

What happens

You ask Claude to "clean up this function." It removes dead code, refactors variable names, adds logging, and reorganizes the method — none of which you asked for. The diff is large, the review is harder than it should be, and the PR has changes you didn't intend.

Why Claude does this

Claude optimizes for "helpful" by default. A function with dead code and inconsistent variable names looks like an invitation to improve. Without explicit scope constraints, Claude treats adjacent improvements as part of the task.

Mitigation

Constrain scope explicitly: "Remove only the unused variables in processPayment(). Do not change logic, add logging, or rename anything else." The more specific the exclusion, the cleaner the diff. Always read the full diff before approving — not just the lines you expected.

Failure mode 5: Architectural authority confusion
Strategic risk

What happens

You ask Claude to "design the caching layer" or "choose the right database for this use case." Claude produces a confident, well-structured answer — but it is optimizing for general best practices, not your team's operational expertise, infrastructure constraints, or organizational risk tolerance.

The real problem

Claude does not know that your team has no experience with Redis Cluster, that your SRE team will not support Cassandra, or that your compliance framework requires all data at rest to stay in a specific region. These constraints are not in your codebase. They are in your organization.

Mitigation

Use Claude to explore options and articulate tradeoffs. Use your team to make architectural decisions. "What are the tradeoffs between Redis and Memcached for our session cache use case?" is a great Claude task. "Which should we use?" is a team decision.

Failure mode 6: Long session drift
Manageable

What happens

After 50+ messages, the earliest context in the session is compressed into a summary. Constraints you stated early in the session — "never modify the public API," "all monetary values use BigDecimal" — may be summarized away. Claude's behavior drifts from your original requirements.

How to recognize it

Claude repeats a mistake you corrected an hour ago. Claude proposes something that violates a constraint you stated at the beginning of the session. The behavior feels inconsistent with earlier turns.

Mitigation

For long tasks, repeat critical constraints periodically: "Reminder: we are not changing the public API." Break very long tasks into discrete sessions with explicit handoff summaries. A fresh session with a clear brief is often more effective than a stale session with drifted context.

Red flags in a live session

🚩 Claude generates code that compiles but fails all tests, with no clear diagnosis

This usually means semantic misunderstanding at the planning stage. Stop. Restart with a narrower scope and more explicit constraints. Do not ask Claude to iterate blindly — that burns tokens without converging.

🚩 Claude repeats the same mistake after you correct it twice

The constraint is not being held in context. State it explicitly at the top of your next message. If it happens a third time, add it to CLAUDE.md and start a fresh session.

🚩 Claude's explanation of a framework behavior doesn't match the official documentation

Trust the documentation, not Claude. Correct Claude explicitly and watch whether it adjusts. If it re-hallucinates, add the correct information as a constraint in your prompt.

🚩 Claude proposes an architectural change you weren't expecting

Do not approve it without understanding it fully. Ask Claude to explain the tradeoffs. Then take the decision to your team. Unexplained architectural proposals are exactly the place where good-sounding-but-wrong decisions get shipped.

🚩 The token cost for this session is 5× what you expected

You have likely allowed Claude to explore broadly when it could have been scoped tightly. Review what drove the cost. Adjust the task structure before continuing.

Question Answer
What models does Claude Code use? As of May 2026: Claude Haiku 4.5 for fast/cheap tasks, Claude Sonnet 4.6 as the default for most interactions, Claude Opus 4.7 for complex reasoning. The CLI selects models based on task complexity unless you override with /model.
How do I set conventions Claude always follows? Write a CLAUDE.md in your project root. Claude reads it at session start. Document code style, naming conventions, forbidden patterns, test requirements, and architectural decisions. This is the highest-leverage 30 minutes you can invest.
Can Claude access the internet? Yes, via WebFetch (fetch a URL) and WebSearch (search the web). Both require approval unless pre-authorized. Use for fetching current documentation, checking API changes, or verifying library versions. Do not use to pull untrusted content directly into code.
How do I control which tools Claude can use? .claude/settings.json (project-level) and ~/.claude/settings.json (user-level) define allowed and denied tools. You can create an allowlist for specific tools, require confirmation for others, and block specific commands entirely.
What is a hook? A shell command that runs automatically on a Claude Code event: PreToolUse, PostToolUse, Stop. Hooks enforce standards deterministically — they run regardless of what Claude proposes. Use them for linting, audit logging, and team notifications.
When should I use a subagent? When the task requires parallel independent research (security + performance + compliance review simultaneously), when results from multiple tools would overflow a single context window, or when you want to protect the main session from intermediate noise. Not for routine edits or single-thread tasks.
How does prompt caching work? If the same large prompt prefix (system prompt + stable context) is used within a 5-minute TTL, subsequent calls cost ~10% of input tokens for the cached portion. Set up with the Anthropic SDK's cache_control parameter. Scheduled agents should always use this for repeated analyses.
What should I never send to Claude Code? Production credentials, API keys, private keys, PII, unredacted customer data, or anything that would cause a compliance violation if it appeared in an Anthropic server log. Use environment variable injection, secrets management systems, and .gitignore. When in doubt, check with your security team before the session, not after.
