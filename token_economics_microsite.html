The mental model

Every token you send is context Claude must process. Every token Claude returns is reasoning you paid for. Waste lives in both directions.

Token cost is not a function of task complexity. It is a function of context size × iterations. A simple task with a bloated context costs more than a complex task with a precise one. Learning to control context size is the single highest-leverage skill in token economics.

Collapse ↑ / Expand ↓
Why this is counterintuitive
Most engineers assume that bigger tasks cost more tokens. In practice, task size is a weak predictor of cost. A junior engineer who types "fix our whole auth system" pays 10× more than a senior who types "fix the token expiry check in JwtValidator.verify() — it's not refreshing tokens within 5 minutes of expiry." The senior knows where the problem is, so Claude never has to look. The junior pays for the search. Token discipline is knowledge discipline.

The three cost drivers

Driver 1: Context width
Biggest lever

What it is

Every token in your prompt and every file Claude reads counts as input. A 500-line file Claude reads but does not need costs roughly 400 input tokens — about $0.0012. Multiply by 20 unnecessary files and you have added $0.024 to a session before Claude has done any work. At scale, this compounds significantly.

How to control it

Point Claude at specific files. Use file paths, function names, and line numbers when you know them. Never ask Claude to "look at the project" when you mean "look at OrderService.java lines 40–120." The difference is 30,000 tokens vs 640 tokens for the same task.

Driver 2: Iteration count
Second lever

What it is

Each back-and-forth adds the full conversation history to the context for the next turn. A 10-turn session on a 2,000-token conversation costs roughly 2K + 4K + 6K + … = 110K tokens just in accumulated context, before any new work happens. Rework cycles are exponentially expensive.

How to control it

Invest in the first prompt. A precise, constraint-rich first prompt that gets the task right on the first pass eliminates the most expensive iterations. Every "no, not like that" costs 1–3× the original task in cumulative context. Plan before you type.

Driver 3: Output verbosity
Controllable

What it is

Output tokens cost 5× input tokens ($15/M vs $3/M). Claude's default output style is thorough — explanations, alternatives, caveats. If you only need the code, you are paying for prose you discard. Claude's explanations are valuable; they are also expensive when you do not need them.

How to control it

Request only what you need. "Give me just the diff, no explanation" cuts output by 60–80% on code tasks. "List only the failing tests, not the passing ones" cuts test output by 90% on green suites. Output format instructions pay for themselves immediately.

The fundamental equation
Cost = (context_size × turns) + (output_size × 5). Every technique in this guide reduces one or more of these three variables. You do not need to use all of them. Pick the highest-leverage ones for your workflow and apply them consistently. A 70% reduction in token spend is achievable in one week of habit change — without reducing the quality of work Claude produces.

Prompt craft

The highest-leverage token saving is the prompt itself. A better prompt costs you 30 seconds and saves thousands of tokens.

Prompt quality and token efficiency are the same thing. A vague prompt forces Claude to explore, clarify, and iterate. A precise prompt lets Claude execute directly. The examples below show real before/after pairs with measured token differences.

Rule 1: Name the file, function, and line

Expensive prompt (~18K tokens)
Efficient prompt (~1.2K tokens)

Rule 2: State constraints upfront, not after

The correction tax
Every constraint you add after Claude has produced output costs you the full response to discard plus a new full response to regenerate. If Claude writes 800 tokens of code and you then say
"oh, also don't use streams"
— you have paid for 800 tokens of waste plus another 800 to redo the work. That is a 100% surcharge for a constraint you could have stated upfront in 5 words. State all constraints in the first message.

States constraints upfront (1× cost)

Turn 3: "Also handle quoted commas."
Turn 4: "And return Optional, not null."
3 regeneration cycles. ~6K tokens.
Turn 1: "Write a method to parse CSV files. Constraints: no external libraries, handle quoted commas, return Optional<List<String[]>>, not null."
1 generation. ~1.8K tokens.

Rule 3: Specify output format to eliminate unwanted prose

Task Without format instruction With format instruction Saving
Run tests, report result Full test output + explanation of each failure + suggestion for each + summary paragraph "List only failing tests: name, line, assertion that failed. No passing tests." ~75% fewer output tokens
Code review Summary, inline comments, explanation of each pattern, alternatives considered, overall assessment "List issues only: severity, file:line, one-line description. No praise, no alternatives." ~60% fewer output tokens
Find all usages of a function Narrative walkthrough of each usage with context and explanation "List as: file:line — one-line description. No prose." ~80% fewer output tokens
Generate a diff Diff + explanation of every change + rationale for each decision "Provide the diff only. No explanation unless I ask." ~70% fewer output tokens
Explain an error Background on the error type, historical context, multiple possible causes, links to documentation "Root cause in 2 sentences. Fix in 3 lines. Nothing else." ~85% fewer output tokens

Rule 4: Use the right model for the task

Haiku 4.5

Cheap and fast

$0.80/M input, $4/M output. Use for: file search, simple edits, formatting, linting, boilerplate generation, test scaffolding. Anything well-defined with a clear correct answer. Switching from Sonnet to Haiku on these tasks cuts cost by ~75%.

Sonnet 4.6

Default for most work

$3/M input, $15/M output. The right choice for: debugging, refactoring, code review, planning, explaining complex code. The accuracy gain over Haiku is worth the cost on tasks requiring genuine reasoning.

Opus 4.7

Reserve for hard problems

$15/M input, $75/M output. Use only when Sonnet demonstrably fails: complex architectural decisions, multi-constraint optimization, adversarial security analysis. At 5× Sonnet's cost, the upgrade must earn its price every time.

The switching habit: Most engineers default to Sonnet for everything and Opus for "important" things. The real optimization is routing well-defined tasks to Haiku. A lint check on Haiku costs $0.002. The same check on Sonnet costs $0.012. Run that 500 times a month and you've saved $5 for no change in outcome. At team scale, systematic model routing is worth auditing explicitly.

Prompt caching

Anthropic's prompt cache turns repeated context from a recurring cost into a one-time investment.

Prompt caching reduces input token cost to roughly 10% for content that was cached in the previous 5 minutes. For scheduled agents, repeated audits, and any workflow that sends the same system context on every call, this is the single biggest cost reduction available — often 70–90% of input cost, with no change in output quality.

Collapse ↑ / Expand ↓
What gets cached

Stable prefix content

The cache stores the longest common prefix of your prompt across calls. Your system prompt, CLAUDE.md contents, architectural documentation, shared codebase context — all of it is cached if it appears first and stays unchanged. The variable part (the specific task) goes at the end and is not cached. This is the right structure anyway for clarity.

TTL and mechanics

5-minute TTL

The cache entry lives for 5 minutes from last use. A session that stays active resets the clock on each call. Scheduled agents that run every 5 minutes stay in cache continuously. Agents that run hourly pay full price on each run unless you explicitly structure for caching with the SDK's cache_control parameter.

Cache-friendly prompt structure

Prompt structure — cache-optimized vs cache-busting
Cache miss
Variable content first: "Today is May 12. Analyze this PR: [diff]. Using our standards: [5KB of standards]."
The date changes daily → prefix never matches → full price every call.
~$0.015 / call × 30 calls/day = $4.50/month
Cache hit
Stable content first: "[5KB of standards] Analyze this PR: [diff]. Today is May 12."
Standards are stable → cached after first call → 90% cheaper on every subsequent call within 5 min.
~$0.0015 / call × 30 calls/day = $0.45/month
Result
Same analysis quality. Same output. $4.05/month saved by reordering the prompt. At team scale (10 engineers × 30 calls/day), that is $40.50/month from a 30-second prompt restructure. 90% saved

SDK usage — enabling cache_control

Anthropic SDK — cache_control parameter
Python + TypeScript 
# Python — mark stable context as cacheable
import anthropic

client = anthropic.Anthropic()

# Load once — this is your stable prefix
system_doc = open("CLAUDE.md").read()
arch_doc   = open("ARCHITECTURE.md").read()

response = client.messages.create(
  model="claude-sonnet-4-6",
  max_tokens=1024,
  system=[
    {
      "type": "text",
      "text": system_doc + arch_doc,
      "cache_control": {"type": "ephemeral"}  # ← mark for caching
    }
  ],
  messages=[
    {"role": "user", "content": variable_task}  # ← goes last, not cached
  ]
)

# Check cache performance
print(response.usage.cache_read_input_tokens)   # tokens served from cache (10% cost)
print(response.usage.cache_creation_input_tokens)  # tokens written to cache (full cost, once)
The cache creation cost: The first call that creates a cache entry costs 25% more than a normal call (cache write overhead). Every subsequent hit costs 10% of normal. Break-even is at 2 hits. Three or more hits and you are saving money. For any task that runs more than twice in 5 minutes, caching pays for itself.

Agent discipline

Agents are the most powerful tool and the most expensive mistake. Use them precisely or not at all.

A multi-agent loop costs 3–10× more than a single focused session for the same task. That multiplier is earned when agents run genuinely parallel work that cannot be sequenced. It is wasted when agents are used because the task felt complex, not because it actually required parallelism.

Collapse ↑ / Expand ↓

When agents earn their cost

The task has genuinely parallel independent branches

Security review + performance analysis + compliance check on the same PR. Each requires different expertise, different file access, different reasoning. Running them sequentially in one session serializes parallel work. Three agents running simultaneously finish in 1/3 the wall-clock time. The 3× token cost is justified by 3× throughput and independent context isolation.

The task overflows a single context window

A 500K-line codebase migration cannot fit in one 200K token context. An orchestrating agent routes subproblems to workers with isolated context. Each worker reads only its assigned module. Total tokens: lower than stuffing everything into one context and watching it summarize itself repeatedly.

You need context isolation to avoid cross-contamination

An Explore agent that searches broadly for a pattern should not pollute the main session's context with thousands of intermediate grep results. The subagent absorbs the noise, returns a clean summary. Your main session stays lean.

When agents waste money

Agent misuse patterns — with cost impact
Mistake
Using an Explore agent to find a file you could locate in 10 seconds with Glob.
"Use an agent to find where we handle user authentication."
Agent spawns, reads dozens of files, returns after 2 minutes.
~$0.80 · could have been $0.003 with Glob
Mistake
Sequential tasks wrapped in parallel agents that block on each other's output.
Agent A finishes writing code → Agent B reviews it → Agent C writes tests based on B's review.
Sequential dependency makes parallelism impossible. You paid 3× for 1× work.
3× cost · 0× speed gain
Mistake
Running an agent loop without a scope constraint, letting it explore indefinitely.
"Audit the entire codebase for security issues." with no file boundary.
Agent reads every file. Finds 200 minor style issues alongside 3 real vulnerabilities. Takes 18 minutes.
~$14 · scoped version: $1.20
Fix
Before spawning an agent, ask: Can I sequence this in a single session? If yes — do not use an agent. Does the agent have a bounded scope? Define file paths or module names before it starts. Are the branches truly independent? If A's output feeds B, use one session with two sequential tasks.
discipline saves 60–90% on agent tasks
Agent for a sequential task ($8.40)
Single session for sequential task ($0.90)
Spawn 3 agents: one to find the bug, one to fix it, one to write tests. Agent 1 finishes → passes result to Agent 2 → Agent 2 finishes → passes to Agent 3. Each agent recreates context from scratch. Total: 3 cold-starts, 3 full context loads.
One session: find the bug (Grep, 1 tool call), fix it (Edit, 1 tool call), write tests (2 Read + 1 Write). Shared context, no cold-starts, no re-reads. Total wall clock: 4 minutes. Same outcome.

CLAUDE.md — your highest-ROI investment

A well-written CLAUDE.md eliminates entire categories of corrections. Each correction you prevent saves 2–5× its own token cost in rework.

CLAUDE.md is loaded at session start. Every rule you document there is a correction you will never pay to make mid-session. The economics are simple: writing a constraint once in CLAUDE.md costs ~50 tokens to store. Not writing it costs 200–2,000 tokens every time Claude violates it and you correct it.

Collapse ↑ / Expand ↓
The compounding return
A fintech team added 12 rules to their CLAUDE.md over two weeks: monetary values use BigDecimal never double, all public methods need Javadoc, test classes follow a specific naming pattern, database calls must include a timeout, no System.out.println (use the logger). Before the CLAUDE.md, they were correcting these in review 8–12 times per week — each correction costing 400–800 tokens in the session. After: zero corrections on any of those patterns. That is 4,000–10,000 tokens of rework eliminated weekly. The CLAUDE.md itself cost 600 tokens to write.

What belongs in CLAUDE.md

Non-obvious code conventions
High value

Document it if Claude gets it wrong even once

Every time you say "actually, we use X not Y" mid-session, that correction belongs in CLAUDE.md. The first violation is the signal. After the first correction, that rule is free to enforce forever via the document.

Examples

Monetary amounts: always BigDecimal, never double or float. Date handling: always Instant or ZonedDateTime, never Date or Calendar. Exceptions: always log before rethrowing. Result types: use Optional, never return null from public methods.

Architecture and module boundaries
High value

Why this saves tokens

Without architecture documentation, Claude reads files to infer structure. With it, Claude knows where things live without reading. A one-paragraph architecture summary can eliminate 5,000–20,000 tokens of exploration on every session that touches unfamiliar parts of the codebase.

What to include

Module names and their purpose. Entry points. Data flow for the 2–3 most common request paths. Which packages are off-limits for modification. Which services own which data. External dependencies and their purpose.

Test and PR requirements
Medium value

What to document

Test naming convention. Minimum coverage expectations. Which test types are required (unit, integration, contract). Whether tests can use mocks or must use real dependencies. PR title format. Required reviewers. Which labels to apply.

Why it matters

Claude generates tests that fit the documentation. Without it, Claude generates tests that fit generic best practices — which may not match your team's conventions. Every convention mismatch is a review comment that costs tokens to address.

CLAUDE.md structure that works

Annotated CLAUDE.md skeleton
Template 
# CLAUDE.md — [Service Name]
# Keep this under 500 lines. Claude reads the whole thing every session.
# Longer CLAUDE.md = more tokens per session. Be concise.

## Architecture
# 1 paragraph. Entry points, module map, data flow.
REST API (Spring Boot 3.2) → Service layer → Repository (JPA/Postgres).
Main entry: PaymentController. Auth via JWT in AuthFilter (before controllers).
External: Stripe API (StripeGateway), SQS for async events (EventPublisher).

## Non-negotiable conventions
# Short bullet list. Each rule saves 1–3 corrections per session.
- Monetary values: BigDecimal only. Never double/float.
- Dates: Instant or ZonedDateTime. Never Date or Calendar.
- Null: Never return null from public methods. Use Optional.
- Exceptions: Log with context before rethrowing. Never swallow silently.
- Logging: SLF4J (log variable, not string concat). Never System.out.

## Testing
- Unit tests: Mockito mocks for dependencies. Class: FooTest.java.
- Integration tests: @SpringBootTest, real DB (Testcontainers). Class: FooIT.java.
- Coverage: 80% minimum on service layer. Check before PR.

## Do not touch
# Files/modules Claude should not edit without explicit instruction.
- db/migrations/ — migration files are append-only, never edit existing.
- AuthFilter.java — security-sensitive, requires senior review before change.

## PR format
Title: [JIRA-KEY] Short description (imperative mood).
Branch: feat/, fix/, chore/ prefix required.
Keep CLAUDE.md under 500 lines. Every line is loaded every session. A 2,000-line CLAUDE.md adds ~1,600 tokens to every session's input cost. That is ~$0.005 per session — $1.50/month at 10 sessions/day. Small, but it compounds. Write the rules that matter. Remove ones that no longer apply. Treat CLAUDE.md like production code: it earns its weight or it gets cut.

Token-efficient pattern library

Twelve reusable prompt patterns, each measured for token impact. Copy, adapt, apply.

Good prompts are reusable. These patterns represent the highest-leverage formulations for common engineering tasks. Each reduces token cost by 40–90% compared to the naive version of the same request.

The pattern behind the patterns
Every efficient prompt has three parts: scope (where to look), task (what to do), and format (how to return it). The naive version of any prompt omits at least one of these. Adding the missing parts takes 10–20 words and saves 40–85% of the response cost. Memorize the structure. Apply it mechanically. The quality of the output will not decrease — it will improve, because Claude has less ambiguity to resolve.

Team budget and governance

Token spend without visibility is token spend without control. Measure before you optimize.

Most teams discover their token economics problem when the monthly invoice surprises them. The engineers spending the most are not the least capable — they are often the most ambitious, running the most complex tasks. The goal of budget governance is not to restrict usage but to ensure that high-spend tasks are delivering proportional value.

Collapse ↑ / Expand ↓
Step 1

Measure first

Enable per-API-key logging in Anthropic's console. Assign one API key per engineer or per workstream. Review usage weekly for the first month. Identify the top 3 cost drivers — they are almost always the same two or three patterns: uncached repeated prompts, unbounded agents, or a few very large exploratory sessions.

Step 2

Set a per-engineer reference spend

After 4 weeks of baseline data, calculate the median cost per engineer per day. Set a soft reference (not a hard limit) at 2× median. Engineers above the reference get a conversation, not a cap. The question is always: "Is this spend producing proportional value?" Sometimes yes. Sometimes it reveals an avoidable pattern.

If the scan catches 0 actionable issues in a stable month, that is $450 of zero-value spend. Audit automated workflows quarterly. Apply prompt caching. Adjust scan frequency to match the rate of meaningful code change.

The five habits that compound into 70% savings

1. Name the file and function before Claude does

You know your codebase. Use that knowledge. Pointing Claude at the right file eliminates the entire exploration cost — often 60–80% of total session tokens on codebase analysis tasks.

2. Write all constraints in the first message

One correction cycle (Claude produces output, you say "actually…", Claude regenerates) costs 2–3× the original task in cumulative context. Constraints stated upfront prevent correction cycles. Pause for 30 seconds before sending. Ask: what will I want to change about Claude's output? State it now.

3. Request terse output unless you need explanation

Output costs 5× input. A habit of ending prompts with "no explanation unless asked" or "diff only" cuts output by 50–80% on code tasks without reducing the utility of the deliverable. You can always ask for the explanation in a follow-up — and often you find you did not need it.

4. Cache your system context for repeated tasks

Any workflow you run more than twice in 5 minutes should use prompt caching. Scheduled scans, repeated analyses, CI integrations. Cache creation costs 25% more. Every hit costs 10% of normal. Break-even at 2 hits. Payback compounds with every run.

5. Maintain a lean CLAUDE.md that eliminates recurring corrections

Every rule in CLAUDE.md is a correction you will never pay for again. Review it monthly. Add rules that eliminated a correction in the past 30 days. Remove rules that no longer apply. Keep it under 500 lines or it starts costing more tokens than it saves.
