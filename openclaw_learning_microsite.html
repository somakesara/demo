01
Foundation

OpenClaw is a personal AI assistant you control. It runs on your device, answers on your channels, and keeps your data yours.

Born from the desire for AI that respects privacy and local autonomy, OpenClaw lets you build intelligent workflows without depending on closed platforms or cloud providers. Fork it, modify it, own it.

Collapse ↑ / Expand ↓
Core value

Self-hosted ownership

Configuration and interaction history live on your machine. Your assistant learns from your behavior. Your data never touches a vendor's cloud. This is not a feature — it is the whole point.

Technical reality

LLM-agnostic

OpenClaw works with Claude, GPT, DeepSeek, or any compatible LLM API. You choose the model. You own the API keys. Swap providers without lock-in or rebuilding your assistant.

What OpenClaw does

Chat interface via your platforms

Connect Signal, Telegram, Discord, or WhatsApp. OpenClaw listens for messages, interprets intent via LLM, executes actions, and responds — all through the messaging apps you already use daily.

Persistent context across sessions

OpenClaw remembers your conversation history. It learns preferences, recurring tasks, and context about your life and work. Your assistant gets better the longer you use it.

Extensible tool calling

Define custom tools and integrations. Trigger scripts, query APIs, control smart home devices, manage calendars — anything you can hook into code, OpenClaw can invoke through natural language.

Privacy-first by design

No analytics. No data collection. No telemetry. OpenClaw does not know who you are unless you tell it. Your data is not aggregated, sold, or used to train other systems.

The GitHub momentum: OpenClaw topped 250K GitHub stars in 60 days — faster adoption than React. The community has built hundreds of integrations, plugins, and forks. Most-starred software project on GitHub as of May 2026.

OpenClaw is designed to be installed and configured with minimal friction. Clone, configure, run. The hardest part is deciding which messaging platform to start with.

Three-step setup

Step 1: Clone and install
5 minutes

What to do

Clone the OpenClaw repository. Install dependencies using your platform's package manager (Python, Node, or Rust — pick one). The project is lightweight and has minimal external requirements.

What you need

Git. Python 3.9+ or Node 18+. An API key from Claude, GPT, or your chosen LLM provider. A messaging app account (Signal, Telegram, Discord, or WhatsApp).

Step 2: Configure LLM and messenger
3 minutes

LLM setup

Create .env with your LLM API key and model choice. OpenClaw supports Claude (recommended), GPT-4, and other models with compatible APIs.

Messenger setup

Connect your messaging platform. For Telegram: create a bot token via BotFather. For Discord: generate an app token. For Signal: link your phone. Each takes 2–3 minutes.

Step 3: Run and test
2 minutes

Start the agent

Run openclaw start. The assistant connects to your messaging platform and begins listening. Send a test message. Verify it responds.

First interaction

Try: "What time is it?" or "Remind me to check email." The assistant responds via your messaging app. Congratulations — you now have a personal AI assistant.

Local vs. cloud: OpenClaw runs entirely on your hardware by default. Your LLM calls go to your chosen provider (Claude, OpenAI, etc.) over HTTPS. The provider never knows about your assistant's configuration or history — just the individual queries you send.

How it works

Three layers: Messaging, reasoning, and action. Understanding the flow helps you build better tools and workflows.

OpenClaw's architecture is deliberately simple. A message arrives. The LLM reasons about intent. Actions execute. Results return. No complex orchestration, no hidden magic.

Message in, action out
1. Receive: Message arrives via Signal, Telegram, Discord, or WhatsApp. OpenClaw's listener captures it. 2. Reason: Message and conversation history are sent to your LLM (Claude recommended). The LLM decides: respond directly, call a tool, or ask for clarification. 3. Act: If a tool is needed, OpenClaw executes it — run a script, query an API, control a device, manage a file. 4. Reply: Result is formatted and sent back via the same channel within seconds.
Component

Messenger adapters

Pluggable drivers for Signal, Telegram, Discord, WhatsApp. Each translates platform-specific message formats into OpenClaw's internal representation. Add support for new platforms by writing a new adapter.

Component

LLM interface

Abstraction layer over LLM APIs. Handles prompt formatting, token counting, context management, and tool calling. Swappable — swap Claude for GPT-4 in one line of configuration.

Component

Tool registry

Central catalog of available actions. Tools can be built-in (send email, query database) or custom (your scripts, webhooks). The LLM knows what tools exist and when to invoke them.

Component

State & persistence

Conversation history, user preferences, learned behaviors — all stored locally in SQLite or your choice of database. State persists across restarts and learns from repeated interactions.

Key design principle: OpenClaw does not attempt to be a general-purpose agent framework. It is optimized for a single user (or small team) with a personal assistant over messaging. This constraint makes it fast, simple, and privacy-respecting — unlike larger frameworks that serve many users and require cloud infrastructure.

Write a custom tool in 5 minutes

Example: Weather tool
Python 
import requests
from openclaw import Tool

class WeatherTool(Tool):
    name = "weather"
    description = "Get current weather for any city"

    def execute(self, city: str) -> str:
        # Fetch from API
        response = requests.get(
            f"https://api.weather.example.com/current",
            params={"city": city}
        )
        data = response.json()
        return f"{city}: {data['temp']}°C, {data['condition']}"

# Register with OpenClaw
openclaw.register_tool(WeatherTool())
Tool discovery: OpenClaw automatically exposes registered tools to the LLM. When you ask "What's the weather in Berlin?", the LLM sees that a weather tool exists, calls it with city="Berlin", and returns the result. You write tools in Python, Node, or Rust — OpenClaw handles the LLM integration.

EXECUTION STRATEGY:
  • Tools 1-2: Sequential (Tool 2 needs Tool 1 result)
  • Tool 3: Parallel (independent, runs while 1-2 execute)
  • Tool 4: Sequential (waits for Tools 1-3)
  • Total: Parallel execution cuts time in half

Advanced: Chaining tools and error handling

Example: Multi-step workflow tool
Python 
class MeetingSchedulerTool(Tool):
    name = "schedule_meeting"
    description = "Schedule a meeting: check availability, find a slot, send invites"

    def execute(self, attendees: list, duration: int) -> str:
        try:
            # Step 1: Query calendar for all attendees
            slots = self.find_common_slots(attendees, duration)
            if not slots:
                return "No common availability found"

            # Step 2: Book the earliest slot
            best_slot = slots[0]
            meeting_id = self.create_meeting(best_slot)

            # Step 3: Send invites to all attendees
            self.send_invites(meeting_id, attendees)

            return f"Meeting scheduled: {best_slot}"
        except Exception as e:
            return f"Failed to schedule: {str(e)}"

Tool best practices

Idempotency: Tools should be safe to call multiple times with the same input. If creating a calendar event fails and retries, don't create a duplicate. Error clarity: Return human-readable error messages, not stack traces. Timeout handling: Long operations should return intermediate results or a status to check later. Logging: Log tool inputs and outputs for debugging (not secrets).

Mental models

A few core ideas that unlock the power of OpenClaw.

These concepts recur across documentation, examples, and community discussions. Internalizing them helps you build better assistants.

Collapse ↑ / Expand ↓

Intent over literal commands

OpenClaw's LLM infers intent from conversational language, not syntax. You say "remind me to call mom tomorrow" not "register_reminder(person='mom', time='tomorrow')". The assistant parses intent and maps it to tools.

Context as memory

OpenClaw maintains conversation history and learned state. Each message carries context of previous exchanges. This lets the assistant infer what you mean from brief follow-ups ("Yeah, do it Tuesday" understands the implicit referent).

Tools are capabilities, not APIs

A tool is not a raw API — it is a capability the assistant can invoke. "Send an email" is a tool. "POST to /api/email" is not. The distinction matters for natural language understanding and safety.

Local-first architecture

OpenClaw prioritizes local computation and storage. Your assistant learns locally. Data is yours. Integrations with external services are opt-in, not mandatory. This is a design choice, not a limitation.

Privacy as a non-negotiable

No tracking. No analytics. No data sharing. OpenClaw does not phone home. Your interactions with your assistant are yours alone. This is enforced in code, not just policy.

Behavior tuning in config.yaml

Personality

Assistant traits

tone: professional, casual, witty. personality: brief or verbose. system_prompt: custom instructions (e.g., "You are a software engineer focused on Python"). These shape how the assistant responds.

Capability

Enabled tools

List which tools are available to your assistant. You can disable tools you do not trust or need. This is your security boundary — only enable integrations you want.

Safety

Guardrails

max_tool_calls_per_message: limit tool invocations to prevent loops. allowed_domains: restrict web access. timeout: kill long-running tools. Sensible defaults are provided.

Learning

Persistence

remember_history: keep conversation history (default: true). context_window_size: how much history to send to LLM. Trade off between learning and token cost.

Model choice matters: Claude (Anthropic) is recommended for reasoning, safety, and instruction-following. GPT-4 is strong for coding tasks. DeepSeek is cost-effective for simple queries. Most users stick with one model, but you can mix — use Claude for complex tasks, cheaper models for simple ones.

Cost analysis and token efficiency

Model Input cost (1M tokens) Output cost (1M tokens) Best for
Claude Sonnet 4.6 $3 $15 Default choice — best reasoning/cost tradeoff
Claude Opus 4.7 $15 $75 Complex reasoning, research tasks
GPT-4o $5 $15 Coding, vision tasks
DeepSeek $0.14 $0.28 High volume, simple queries, budget-constrained

Cost optimization tactics

1. Implement context pruning: Keep conversation history under 10K tokens. Archive old chats monthly. 2. Use batch APIs: For non-real-time tasks (reports, summaries), use batch APIs (10x cheaper). 3. Route intelligently: Simple queries (weather, time) hit cheap models. Complex queries (reasoning, planning) hit Claude Sonnet. 4. Cache system prompts: Use prompt caching if your provider supports it — repeating system instructions are 90% cheaper.

Real cost example: A user running OpenClaw 8 hours/day with Claude Sonnet costs ~$12/month (assuming average query is 500 input tokens, 200 output tokens). Comparable commercial AI assistants cost $20+/month. Self-hosted option (Ollama + local LLM) costs $0/month but requires a GPU.

When it breaks

OpenClaw fails in predictable ways. Knowing these patterns prevents surprises in production.

No software is bulletproof. Understanding failure modes helps you design safer workflows and set appropriate expectations.

Collapse ↑ / Expand ↓

1. LLM hallucination and tool misuse

Pattern: Wrong tool invoked or parameters misunderstood. "Create user" → delete operation.
Fix: Confirmation prompts for destructive ops. Unambiguous tool descriptions. Staging tests. Audit logs.

2. Tool latency and timeouts

Pattern: Tool takes >30s, LLM retries, duplicate actions occur. Email sent twice.
Fix: Per-tool timeout settings. Idempotent tools. Job queues for long ops.

3. Context window exhaustion

Pattern: Conversation grows too large, context overflows, assistant forgets prior decisions.
Fix: Configure context_window_size. Archive old chats. Auto-summarize long contexts.

4. Credential exposure

Pattern: API keys logged, leaked in errors, or sent to untrusted services.
Fix: Never log secrets. Use .env (gitignored). Rotate regularly. Short-lived tokens only.

5. Network unavailability

Pattern: LLM provider unreachable, messenger disconnects, messages lost.
Fix: Local LLM fallbacks. Message queuing. Graceful offline handling.

6. Tool permission escalation

Pattern: Innocent request chains tools for unintended action. "What's in my email?" → forwarded elsewhere.
Fix: Least privilege. Segregate sensitive tools. Opt-in for multi-step.

Safe production rule: Never give OpenClaw access to tools it doesn't absolutely need. Start with read-only tools (fetch, query, summarize). Only enable write operations (send, modify, delete) after proven testing. Audit logs are not optional — they're your safety net.

Threat model and defenses

OpenClaw operates across three trust boundaries. Understanding them is non-negotiable for sensitive use cases.

Local-first architecture simplifies security, but does not eliminate risk. Here's where risks lie and how to mitigate them.

Collapse ↑ / Expand ↓
Boundary 1

Local machine

Your assistant runs on your device. If the device is compromised (malware, physical access), the assistant can be weaponized. Mitigation: Use OS-level security (firewall, file permissions, disk encryption). Run OpenClaw in a restricted user account, not as admin.

Boundary 2

LLM provider

Messages are sent to Claude, GPT, or your chosen provider. The provider can theoretically see all queries. Mitigation: Anthropic's Claude does not train on API calls by default. Use on-device models (Ollama, LLaMA) for maximum privacy. Redact sensitive data before sending.

Boundary 3

External tools and APIs

Tools integrate with third-party services (GitHub, Slack, email). These tools see requests and responses. Mitigation: Minimize tool scope. Never pass full credentials — use API keys with narrow scopes. Use VPNs and encrypted channels for sensitive APIs.

Risk: Credential theft

API keys in config

If .env or config.yaml is exposed (git, backup, screen sharing), all credentials are compromised. Mitigation: Never commit secrets. Use .gitignore. Rotate keys after any exposure. Use secret management tools (Vault, 1Password) instead of plain files.

Security checklist for production

✓ Secrets management

Store API keys in environment variables, not config files. Use a secret manager (Vault, 1Password Secrets) for shared teams. Rotate keys monthly. Monitor for exposed keys in git history.

✓ Tool whitelisting

Enable only tools your workflow needs. Document which tools have write access. Require explicit confirmation for destructive operations (delete, modify, send).

✓ Audit logging

Log all tool invocations, parameters, and results. Store logs securely. Review them weekly. Alerts should fire on unusual patterns (mass deletions, unexpected API calls).

✓ Message encryption

For sensitive channels (Signal is built-in), ensure end-to-end encryption. Avoid SMS or unencrypted Telegram. Store conversation history encrypted at rest.

✓ Network isolation

Run OpenClaw on a dedicated, low-privilege user account. Use firewalls to restrict which APIs it can reach. Consider network segmentation for multi-tool deployments.

✓ Monitoring and alerting

Alert on token limit hits (context exhaustion). Alert on API errors and retries. Alert on unusual tool chaining. Set up dead-man's switch to verify assistant is healthy.
